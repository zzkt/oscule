#+title: Oscule Progress

* Bugs

** [2026-06-21] float64 denormal rounding and scaling (osc.janet lines 94-112)

The =float64-raw= function had two bugs in the denormal encoding path:

1. ~Scaling:~ Used =(1 + m) * 2^52= for denormals, but IEEE 754 denormals
   store the mantissa scaled by =2^(be + 51)= (where be is the biased
   exponent, ranging from -51 to 0 for float64 denormals).  This caused
   all denormals to produce mantissa values =2^52= too large, which when
   masked to 52 bits gave complete garbage (or zeros for small values).

2. ~Rounding:~ The =math/trunc= without =+ 0.5= could truncate downward
   for values with a fractional part in the scaled mantissa.  Same class
   of bug as the float32 fix from 2026-06-18.

~Fix:~ Replaced the fixed =2^52= scaling with =pow2-table[shift]= where
=shift = (if (< be 1) (+ be 51) 52)=, and added =+ 0.5= rounding.

~Impact:~ The smallest float64 denormal =(math/pow 2 -1074)= encoded to
all zeros (decoded as 0.0).  All ~10 000 fuzz-generated denormals now
round-trip correctly.

** [2026-06-21] float32 denormal scaling (osc.janet lines 62-76)

Same scaling bug as float64: used =(1 + m) * 2^23= but IEEE 754
float32 denormals need =(1 + m) * 2^(be + 22)=.  The existing masked
encoding =(band ... f32-mantissa-mask)= accidentally gave the right
answer for the largest denormals but failed for smaller ones.
The smallest float32 denormal (=2^(-149)=) would encode to 0.

~Fix:~ Same approach as float64 — use =pow2-table[shift]= with
=shift = (if (< be 1) (+ be 22) 23)=.

~Impact:~ Not user-visible yet (float32 denormals are below the normal
range covered by =float32-min= and were never tested), but correctness
is required for bit-exact IEEE 754 interop.

** [2026-06-18] float32 rounding (src line 69)

The =float32-raw= function used =math/trunc= to extract the mantissa from
the scaled fraction (=(* frac mantissa-23)=). For values like 3.14 the
fractional part × 8388608 gave 1170123.xx and =trunc= discarded the
fractional part, producing 1170123 instead of the correct 1170124.

~Fix:~ =math/trunc (+ (* frac mantissa-23) 0.5)= rounds to nearest.

~Impact:~ Byte-level interop with cl-osc was broken for float32 values
whose scaled fraction had nonzero fractional part (nearly all non-integer
floats not exactly representable in IEEE 754.

- ~float-normalize~ correctly handles denormals, zero, infinity, and NaN
- =float32-raw= is also used by =encode-float32= (and transitively by
  =encode-message=)
- =raw-to-float32= (decode direction) was correct

** [2026-06-18] padded-length off-by-4 on aligned strings (src lines ~130-141)

=padded-length= added an extra 4 bytes when the input was already 4-byte
aligned.  This was correct for the encode-path call site (=pad4=, which
receives raw string length and must add NUL + padding), but wrong for the
decode-path call site (=decode-args=, which supplies the position already
including the NUL terminator).

When a 3-char string (e.g. "two") was immediately followed by a float
argument, =decode-args= would skip past the next argument because
padded-length(28) returned 32 instead of 28 (28 = 24 + 3 + 1 was already
aligned).  This caused mixed messages with aligned strings to decode
incorrectly.

~Fix:~
1. Made =padded-length= the canonical round-up-to-4 function (returns
   =n= when already aligned).
2. Updated =pad4= to pass =(inc (length s))= instead of =(length s)=
   to account for the NUL terminator separately.
3. Removed the now-redundant =padded-end= function (same logic).

~Impact:~ Mixed messages like =(encode-message "/test" 1 "two" 3.14)=
would produce garbage for the float arg on decode.  Also broke interop
with cl-osc for any message containing a string whose padded length
equalled its content length + NUL (i.e. any string whose length mod 4
== 3).

* Benchmarks

Run with =janet test/benchmark.janet= and =sbcl --load test/benchmark.lisp=.

100 000 iterations per test, μs/call (lower is better).

** encode (scalar)

| operation            | oscule (janet) | cl-osc (sbcl) | ratio (janet / sbcl) |
|----------------------+----------------+---------------+----------------------|
| encode-int32         |         0.100  |         0.008 |                12.5x |
| encode-float32       |         0.454  |         0.010 |                45.4x |
| encode-string        |         0.460  |         0.403 |                 1.1x |
| encode-int64         |         0.465  |         0.009 |                51.7x |

SBCL native-compiled numeric encoding is ~10-50x faster, but string
encoding (which involves allocation and padding) is on par.

** encode (message)

| operation                | oscule (janet) | cl-osc (sbcl) | ratio (janet / sbcl) |
|--------------------------+----------------+---------------+----------------------|
| encode int msg           |         1.732  |         1.516 |                 1.1x |
| encode float msg         |         2.138  |         1.414 |                 1.5x |
| encode mixed (i+s+f)     |         3.254  |         2.448 |                 1.3x |
| encode big (10 args)     |         6.254  |         6.525 |                 1.0x |
| encode long string       |         3.733  |        10.701 |                 0.3x |

Message-level encoding is close or faster in oscule. The gap narrows
because message construction overhead (address padding, tag string,
arg dispatch) dominates the per-element encoding cost.  Long-string
encoding favours oscule because janet's =string/repeat= avoids the
SBCL per-character loop.

| decode-string        |         0.253  |         0.282 |                 0.9x |
| decode-int64         |         0.186  |         0.081 |                 2.3x |

SBCL is faster for numeric decode (native byte-order ops) but string

** decode (message)

| operation                | oscule (janet) | cl-osc (sbcl) | ratio (janet / sbcl) |
|--------------------------+----------------+---------------+----------------------|
| decode int msg           |         1.296  |         0.969 |                 1.3x |
| decode float msg         |         1.376  |         1.036 |                 1.3x |
| decode mixed (i+s+f)     |         2.016  |         1.446 |                 1.4x |
| decode big (10 args)     |         3.767  |         2.916 |                 1.3x |
| decode long string       |         7.992  |        10.032 |                 0.8x |

Message decode is within ~1.5x of SBCL across the board.  Long-string
decode favours janet because oscule's =decode-string= is a pure-janet
while loop (no type dispatch or alien calls).

** summary

- Encode/decode is 1-2x SBCL speed for real-world message workloads.
- Scalar numeric encode is 10-50x slower (expected: janet is
  bytecode-interpreted, SBCL is native-compiled).
- String and message-level operations are on par or faster.
- For OSC workloads (predominantly messages, not raw scalar loops)
  oscule performance is practical for real-time audio use.

** compiled bytecode

Janet /always/ compiles source to bytecode before execution — there is no
"interpreted mode" to compare against.  The =janet -c= flag pre-compiles a
.jimage bytecode bundle (for use with =janet -i=) but the bytecode
produced is identical, so execution speed is the same either way.

The practical difference: a .jimage loads ~7× faster because it skips the
compile-from-source step (see startup time below).

** module dispatch overhead

| operation           | module (μs) | local alias (μs) | overhead |
|---------------------+-------------+------------------+----------|
| encode-int32        |       0.109 |            0.083 |     1.3× |
| encode-float32      |       0.476 |            0.469 |     1.0× |
| encode-string       |       0.460 |            0.462 |     1.0× |
| encode mixed msg    |       3.305 |            3.244 |     1.0× |
| decode mixed msg    |       2.119 |            2.018 |     1.0× |

Module lookup overhead is negligible (≤1.3×) and vanishes on
message-level operations where dispatch dominates.

** inline hot functions

A self-contained inline version of =float32-raw= was compared against the
module version (=encode-float32= delegates to =float32-raw= internally):

| version            | encode float32 (μs) |
|--------------------+---------------------|
| module             |               0.444 |
| inline raw32       |               0.500 |
| encode via raw32   |               0.589 |

The module version is slightly faster — module-level functions avoid
closure overhead from nested =defn= inside =defn=.

** startup time

| load method | 100 loads | per load |
|-------------+-----------+----------|
| dofile source | 82.7 ms | 0.83 ms |
| jimage (-i)   | n/a¹     | n/a     |

¹ =dofile= cannot load .jimage.  The =janet -i= flag loads a jimage as
  the main script; functions are available but can't be benchmarked
  externally.  Source loading is fast enough (~0.8 ms) for most use.

** summary

All the relevant results are in the original =benchmark.janet= vs
=benchmark.lisp= comparison.  The compiled-bytecode investigation
confirmed that:
1. Janet always compiles to bytecode — no separate compile step needed.
2. Module dispatch overhead is negligible (≤1.3×).
3. Inline hot functions are no faster (module level wins).
4. jimage files only speed up load time, not execution.
